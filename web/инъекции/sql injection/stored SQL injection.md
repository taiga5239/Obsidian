[[SQL-injection]]

Инъекция, также известная как хранимая SQL-инъекция, использует уязвимости, при которых предоставленные пользователем данные сохраняются и впоследствии используются в другой части приложения, возможно, после некоторой предварительной обработки. Этот тип атаки более коварен, поскольку вредоносный SQL-код не обязательно должен немедленно приводить к синтаксической ошибке SQL или другим очевидным проблемам, что затрудняет его обнаружение с помощью стандартных методов проверки входных данных. Инъекция происходит при втором использовании данных, когда они извлекаются и используются в SQL-команде, отсюда и название « второго порядка ».

==🔴Опасность== SQL-инъекции второго порядка заключается в ее способности обходить типичные средства защиты на этапе ввода, такие как базовая проверка или очистка входных данных, которые происходят только на этапе первоначального ввода данных. Поскольку полезная нагрузка не вызывает сбоев на первом этапе, ее можно пропустить до тех пор, пока не станет слишком поздно, что делает атаку особенно скрытной.

Пример добавления книг:

PHP Фрагмент кода, используемый в нашем приложении для добавления книг:
```php
if (isset($_POST['submit'])) {

    $ssn = $conn->real_escape_string($_POST['ssn']);

    $book_name = $conn->real_escape_string($_POST['book_name']);

    $author = $conn->real_escape_string($_POST['author']);

    $sql = "INSERT INTO books (ssn, book_name, author) VALUES ('$ssn', '$book_name', '$author')";

    if ($conn->query($sql) === TRUE) {

        echo "<p class='text-green-500'>New book added successfully</p>";

    } else {

        echo "<p class='text-red-500'>Error: " . $conn->error . "</p>";

    }

}
```

В коде используется `real_escape_string()` метод экранирования специальных символов во входных данных. Хотя этот метод может снизить некоторые риски немедленной SQL-инъекции за счет экранирования одинарных кавычек и других метасимволов SQL, он не защищает приложение от SQL-инъекций второго порядка. Ключевая проблема здесь — отсутствие параметризованных запросов, что крайне важно для предотвращения атак SQL-инъекций. При вставке данных с использованием этого real_escape_string()метода они могут содержать символы полезной нагрузки, которые не причиняют немедленного вреда, но могут быть активированы при последующем извлечении и использовании в другом SQL-запросе. Например, вставка книги с именем, например, `Intro to PHP'; DROP TABLE books;-`-может не повлиять на операцию INSERT , но может иметь серьезные последствия, если имя книги позже будет использовано в другом контексте SQL без надлежащей обработки.

***Первоначальная вставка полезной нагрузки :*** добавляется новая книга, в которую `12345'; UPDATE books SET book_name = 'Hacked'; --` вставляется полезная нагрузка ssn. Точка с запятой ( ;) используется для завершения текущего SQL-запроса.

***Вредоносное выполнение SQL-запроса :*** После этого, когда администратор или любой другой пользователь переходит по указанному URL-адресу  `http://10.113.141.82/second/update.php` и обновляет книгу, внедренная полезная нагрузка выходит за рамки предполагаемой структуры SQL-команды и внедряет новую команду, которая обновляет все записи в таблице книг.  
Код обновления книг:
```
if ( isset($_POST['update'])) {
    $unique_id = $_POST['update'];
    $ssn = $_POST['ssn_' . $unique_id];
    $new_book_name = $_POST['new_book_name_' . $unique_id];
    $new_author = $_POST['new_author_' . $unique_id];

    $update_sql = "UPDATE books SET book_name = '$new_book_name', author = '$new_author' WHERE ssn = '$ssn'; INSERT INTO logs (page) VALUES ('update.php');";
..
...
```

***Закомментирование остальной части :*** Двойное тире ( --) — это символ комментария в SQL. Все, что следует за ним, --будет проигнорировано SQL-сервером, что фактически нейтрализует любые оставшиеся части исходного SQL-запроса, которые могли бы вызвать ошибки или раскрыть атаку. После выполнения приведенного выше запроса названия всех книг изменятся на " взломанные"
