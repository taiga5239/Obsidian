==🔴HTTP== сообщения представляют собой пакеты данных, которыми обмениваются пользователь (клиент) и веб-сервер

Существует два типа HTTP-сообщений:

- **HTTP-запросы** : отправляются пользователем для запуска действий в веб-приложении.
- **HTTP-ответы** : отправляются сервером в ответ на запрос пользователя.

![[Pasted image 20261103203339.png]]

Начальная строка — это своего рода введение к сообщению. Она указывает, какой тип сообщения отправляется — запрос от пользователя или ответ от сервера. Эта строка также содержит важные сведения о том, как следует обрабатывать сообщение.

Заголовки представляют собой пары «ключ-значение», которые предоставляют дополнительную информацию о HTTP-сообщении. Они дают инструкции как клиенту, так и серверу, обрабатывающему запрос или ответ. Эти заголовки охватывают самые разные аспекты, такие как безопасность, типы контента и многое другое, обеспечивая бесперебойную передачу данных.

Пустая строка — это небольшой разделитель, отделяющий заголовок от тела сообщения. Она необходима, поскольку показывает, где заканчиваются заголовки и где начинается фактическое содержимое сообщения. Без этой пустой строки сообщение может быть искажено, и клиент или сервер могут неправильно его интерпретировать, что приведет к ошибкам.

Тело запроса — это место, где хранятся фактические данные. В запросе тело может содержать данные, которые пользователь хочет отправить на сервер.

 ==🔴**HTTP request**== это то, что пользователь отправляет веб-серверу для взаимодействия с веб-приложением и выполнения определённых действий.
![[Pasted image 20261103203738.png]]

==🔵Метод **HTTP**== сообщает серверу, какое действие пользователь хочет выполнить с ресурсом, указанным в URL-адресе.

- **GET-запрос**  
	Используется для получения данных с сервера без внесения каких-либо изменений. Напоминание! Убедитесь, что вы предоставляете доступ только тем пользователям, которым это разрешено. Избегайте включения конфиденциальной информации, такой как токены или пароли, в GET-запросы, поскольку они могут отображаться в открытом виде.

- **POST-запрос**
	Отправляет данные на сервер, обычно для создания или обновления чего-либо. Напоминание! Всегда проверяйте и очищайте входные данные, чтобы избежать таких атак, как SQL-инъекции или XSS.

- **PUT**  
	Заменяет или обновляет что-либо на сервере. Напоминание! Убедитесь, что пользователь имеет право вносить изменения, прежде чем принимать запрос.

- **Команда DELETE** 
	Удаляет данные с сервера. Напоминание! Как и в случае с командой PUT, убедитесь, что удалять ресурсы могут только авторизованные пользователи.

Помимо этих распространенных методов, в конкретных случаях используются и другие:

- **PATCH**
	Это обновление части ресурса. Оно полезно для внесения небольших изменений без полной замены, но всегда проверяйте данные во избежание несоответствий.

- **HEAD**
	Работает аналогично GET, но извлекает только заголовки, а не всё содержимое. Это удобно для проверки метаданных без загрузки полного ответа.

- **Параметр OPTIONS**
	Показывает, какие методы доступны для конкретного ресурса, помогая клиентам понять, что они могут делать с сервером.

- **TRACE**
	Подобно OPTIONS, показывает, какие методы разрешены, часто для отладки. Многие серверы отключают его по соображениям безопасности.

- **CONNECT** 
	Используется для создания защищенного соединения, например, для HTTPS. Это не так распространенный, но критически важный параметр для зашифрованной связи.

Каждый из этих методов имеет свой собственный набор правил безопасности. Например, запросы PATCH следует проверять во избежание несоответствий, а параметры OPTIONS и TRACE следует отключать, если они не нужны, чтобы избежать возможных угроз безопасности.

Путь ==🔵**в URL-адресе**== указывает серверу, где найти ресурс, который запрашивает пользователь.

В поле « **==🔵Версия HTTP==» отображается** версия протокола, используемого для связи между клиентом и сервером. 

- **HTTP/0.9** (1991)  
	Первая версия, поддерживала только GET-запросы.

- **HTTP/1.0** (1996)  
	Добавлены заголовки и улучшена поддержка различных типов контента, что повысило качество кэширования.

- **HTTP/1.1** (1997)  
	обеспечил постоянные соединения, кодирование передачи данных по частям и улучшенное кэширование. Он до сих пор широко используется.

- **В HTTP/2** (2015)  
	были введены такие функции, как мультиплексирование, сжатие заголовков и приоритезация для повышения производительности.

- **HTTP/3** (2022)  
	Создан на основе HTTP/2, но использует новый протокол (QUIC) для более быстрых и безопасных соединений.


==🔴Заголовки запроса== позволяют передавать веб-серверу дополнительную информацию о запросе.

- Host
	Указывает имя веб-сервера, к которому направлен запрос.

- User-Agent
	Предоставляет информацию о веб-браузере, из которого поступает запрос.

- Referer
	Указывает URL-адрес, с которого поступил запрос.

- Cookie
	Информация, которую веб-сервер ранее запросил у веб-браузера для сохранения, хранится в файлах cookie.

- Content-Type
	Указывает, какой тип или формат данных содержится в запросе.

В HTTP-запросах, таких как POST и PUT, где данные отправляются на веб-сервер, а не запрашиваются с него, данные находятся внутри ==🔴тела HTTP-запроса.==

- **URL-кодированный формат (application/x-www-form-urlencoded) —** формат, в котором данные структурированы в виде пар ключ-значение, где ( `key=value`). Несколько пар разделены символом ( `&`), например  `key1=value1&key2=value2`, . Специальные символы кодируются процентами.
```
POST /profile HTTP/1.1
Host: tryhackme.com
User-Agent: Mozilla/5.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 33

name=Aleksandra&age=27&country=US
```

- **Форматирование данных (multipart/form-data)** позволяет отправлять несколько блоков данных, каждый из которых разделяется строкой-разделителем. Строка-разделитель — это определенный заголовок самого запроса. Этот тип форматирования можно использовать для отправки двоичных данных, например, при загрузке файлов или изображений на веб-сервер.
```
POST /upload HTTP/1.1
Host: tryhackme.com
User-Agent: Mozilla/5.0
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="username"

aleksandra
----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="profile_pic"; filename="aleksandra.jpg"
Content-Type: image/jpeg

[Binary Data Here representing the image]
----WebKitFormBoundary7MA4YWxkTrZu0gW--
```

- **JSON (application/json)** В этом формате данные могут передаваться с использованием структуры JSON (JavaScript Object Notation). Данные форматируются парами «имя:значение». Несколько пар разделяются запятыми и заключаются в фигурные скобки { }.
```
POST /api/user HTTP/1.1
Host: tryhackme.com
User-Agent: Mozilla/5.0
Content-Type: application/json
Content-Length: 62

{
    "name": "Aleksandra",
    "age": 27,
    "country": "US"
}
```

- **XML (application/xml)**  В формате XML данные структурируются внутри меток, называемых тегами, которые имеют открывающую и закрывающую части. Эти метки могут быть вложенными друг в друга.
```
POST /api/user HTTP/1.1
Host: tryhackme.com
User-Agent: Mozilla/5.0
Content-Type: application/xml
Content-Length: 124

<user>
    <name>Aleksandra</name>
    <age>27</age>
    <country>US</country>
</user>
```


Первая строка в каждом HTTP-ответе называется ==🔴**строкой состояния (Status Line)**== . Она содержит три ключевых элемента информации:

1. **Версия HTTP** : Эта информация показывает, какая версия HTTP используется.
2. **Код состояния** : трёхзначное число, указывающее на результат вашего запроса.
3. **Краткое пояснение** : Короткое сообщение, объясняющее код состояния в удобочитаемой форме.

==🔵Код **состояния**== — это число, указывающее на успешность или неудачу запроса, а фраза **- обоснование** объясняет произошедшее. Эти коды делятся на пять основных категорий:

- **Информационные ответы (100-199)**  
	Эти коды означают, что сервер получил часть запроса и ожидает ответа. Это сигнал "продолжай в том же духе".

- **Успешные ответы (200-299)**  
	Эти коды означают, что все прошло как ожидалось. Сервер обработал запрос и отправил запрошенные данные.

- **Сообщения о перенаправлении (300-399)**  
	Эти коды указывают на то, что запрошенный вами ресурс перемещен в другое место, обычно с указанием нового URL-адреса.

- **Коды ошибок клиента (400-499)**  
	указывают на проблему с запросом. Возможно, URL-адрес указан неверно или отсутствует необходимая информация, например, данные для аутентификации.

- **Коды ошибок сервера (500-599)**  
	означают, что сервер столкнулся с ошибкой при попытке выполнить запрос. Обычно это проблемы на стороне сервера, а не по вине клиента.

Когда веб-сервер отвечает на запрос HTTP в запросе содержатся ==🔴**заголовки HTTP-ответа**==, которые, по сути, представляют собой пары «ключ-значение».

***Обязательные заголовки ответа***

- **Дата**
	Этот заголовок показывает точную дату и время, когда сервер сгенерировал ответ.

- **Content-Type**
	Он сообщает клиенту, какой тип контента он получает, например, HTML, JSON или что-то другое. Он также включает кодировку символов (например, UTF-8), чтобы помочь браузеру правильно отобразить его.

- **Сервер**
	Этот заголовок показывает, какое серверное программное обеспечение обрабатывает запрос. Он полезен для отладки, но также может раскрыть информацию о сервере, которая может быть полезна для злоумышленников, поэтому многие удаляют или скрывают этот заголовок.

Помимо основных заголовков, существуют и другие распространенные заголовки, которые предоставляют клиенту или браузеру дополнительные инструкции и помогают контролировать обработку ответа.

- **Set-Cookie** 
    Эта команда отправляет cookie-файлы с сервера на клиент, который затем сохраняет их и отправляет обратно с последующими запросами. Для обеспечения безопасности убедитесь, что cookie-файлы установлены с `HttpOnly`флагом (чтобы к ним не мог получить доступ JavaScript) и `Secure`флагом (чтобы они отправлялись только по HTTPS).
    
- **Cache-Control**
    Этот заголовок сообщает клиенту, как долго он может кэшировать ответ, прежде чем снова обратиться к серверу. При необходимости он также может предотвратить кэширование конфиденциальной информации (используя `no-cache`).
    
- **Location** 
    Этот заголовок используется в ответах перенаправления (3xx). Он сообщает клиенту, куда перейти дальше, если ресурс переместился. Если пользователи могут изменять этот заголовок во время запросов, будьте осторожны при его проверке и очистке — в противном случае вы можете столкнуться с открытыми уязвимостями перенаправления, когда злоумышленники могут перенаправлять пользователей на вредоносные сайты.

В теле HTTP **-ответа** содержатся фактические данные.

***Заголовки безопасности***

Заголовки безопасности помогают повысить общую безопасность веб-приложения, обеспечивая защиту от таких атак, как межсайтовый скриптинг (CSS, XSS).

==🔴Заголовки безопасности:==

- Политика безопасности контента (CSP)
- Строгая транспортная безопасность (HSTS)
- X-Content-Type-Options
- Политика реферера

==🔵Политика безопасности контента (CSP)==
***Заголовок CSP*** — это дополнительный уровень безопасности, который помогает смягчить последствия распространенных атак, таких как межсайтовый скриптинг (XSS). Вредоносный код может быть размещен на отдельном веб-сайте или домене и внедрен в уязвимый веб-сайт. CSP позволяет администраторам определять, какие домены или источники считаются безопасными, и обеспечивает дополнительный уровень защиты от подобных атак.

В самом заголовке вы можете увидеть такие свойства, как `default-src`, `script-src` и многие другие. Каждое из них позволяет администратору на разных уровнях детализации определять, какие домены разрешены для какого типа контента. Использование `self` — это специальное ключевое слово, отражающее тот же домен, на котором размещен веб-сайт.

Рассмотрим пример заголовка CSP:

`Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.tryhackme.com; style-src 'self'

Мы видим применение:

- **default-src**  
    — параметр, определяющий политику по умолчанию для self, что означает отображение только текущего веб-сайта.  
      
    
- **script-src**  
    — параметр, определяющий правила загрузки скриптов, включая скрипты, размещенные на собственном сервере и на других ресурсах.`https://cdn.tryhackme.com`  
      
    
- **style-src**  
    — параметр, определяющий правила загрузки таблиц стилей CSS с текущего веб-сайта (самого сайта).

==🔵Строгая транспортная безопасность (HSTS)==

Заголовок HSTS гарантирует, что веб-браузеры всегда будут подключаться по протоколу HTTPS. Рассмотрим пример использования HSTS:

`Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`

Вот подробный разбор заголовка HSTS по директивам:

- **max-age**  
    — это время истечения срока действия данного параметра в секундах.  
      
- **includeSubDomains**  
    — необязательный параметр, указывающий браузеру применять этот параметр ко всем поддоменам.  
      
- **Предварительная загрузка**
    — этот необязательный параметр позволяет включать веб-сайт в списки предварительной загрузки. Браузеры могут использовать списки предварительной загрузки для принудительного использования HSTS еще до первого посещения веб-сайта.

==🔵X-Content-Type-Options==

Заголовок X-Content-Type-Options можно использовать, чтобы указать браузерам не определять MIME-тип ресурса методом случайного выбора, а использовать только заголовок Content-Type. Вот пример:

`X-Content-Type-Options: nosniff`

- **nosniff**  
    — Эта директива указывает браузеру не перехватывать и не угадывать значения МИМE.

==🔵Политика реферера==

Этот заголовок определяет объем информации, отправляемой на целевой веб-сервер при перенаправлении пользователя с исходного веб-сервера, например, при нажатии на гиперссылку. Заголовок позволяет веб-администратору контролировать, какая информация передается. Вот несколько примеров заголовка Referrer-Policy:

- `Referrer-Policy: no-referrer`
- `Referrer-Policy: same-origin`
- `Referrer-Policy: strict-origin`
- `Referrer-Policy: strict-origin-when-cross-origin`

Вот разбивка заголовка Referrer-Policy по директивам:

- **no-referrer**  
    - Эта опция полностью отключает отправку любой информации о реферере.  
      
- **same-origin**  
    — Эта политика будет отправлять информацию о реферере только в том случае, если целевой сайт является частью того же источника. Это полезно, если вы хотите, чтобы информация о реферере передавалась, когда гиперссылки находятся внутри одного веб-сайта, но не за его пределами, на внешние веб-сайты.  
      
- **strict-origin**  
    — Эта политика отправляет реферер в качестве источника только тогда, когда протокол остается неизменным. Таким образом, реферер отправляется, когда HTTPS-соединение переходит к другому HTTPS-соединению.  
      
- **strict-origin-when-cross-origin**  
    — это аналогично strict-origin, за исключением запросов из одного источника, где в заголовке origin отправляется полный путь URL-адреса.
