==🔴Нарушение контроля доступа== — это тип уязвимости безопасности, возникающий, когда приложение или система не обеспечивает надлежащего ограничения доступа к конфиденциальным данным или функциям. Эта уязвимость позволяет злоумышленникам получить несанкционированный доступ к ресурсам, доступ к которым должен быть ограничен, таким как учетные записи пользователей, файлы, базы данных или административные функции. Нарушение контроля доступа может происходить по разным причинам, включая плохой дизайн, ошибки конфигурации или ошибки в коде.

IDOR Уязвимые точки не ограничиваются параметрами URL, видимыми в адресной строке браузера. Они могут находиться везде, где приложение обрабатывает предоставленную пользователем ссылку на объект. Ограничение тестирования только адресной строкой приведет к тому, что значительная часть уязвимостей IDOR останется незамеченной.

Современные веб-приложения загружают данные ==🔵динамически асинхронно==. HTTP Запросы, которые браузер отправляет в фоновом режиме. При отображении страницы может быть инициировано несколько процессов API. Эти запросы используются для получения отображаемых данных. Они никогда не отображаются в адресной строке, но полностью видны в инструментах разработчика браузера на вкладке **«Сеть»** , а также в перехватывающих прокси-серверах, таких как Burp Suite.

Файлы ==🔵JavaScript==, загружаемые приложением, часто содержат ссылки на конечные точки API и имена параметров, которые не отображаются в видимом интерфейсе. Проверка этих файлов (вручную или с помощью автоматизированных инструментов) может выявить конечные точки, с которыми разработчик не предполагал прямого взаимодействия пользователей.

Некоторые конечные точки принимают параметры, которые фронтенд никогда не отправляет. Эти параметры могли быть введены в процессе разработки для отладки или тестирования и никогда не удалялись до развертывания. Например, конечная точка `/user/details`обычно может возвращать профиль текущего пользователя, основываясь исключительно на cookie-файле сессии, без идентификатора в запросе. Однако добавление идентификатора `?user_id=123`к URL-адресу может привести к тому, что конечная точка учтет этот параметр и вернет запись другого пользователя. Этот метод, известный как **анализ параметров** , является распространенным способом выявления скрытых векторов IDOR, которые в противном случае остались бы незамеченными.

Нарушение контроля доступа происходит, когда сервер некорректно определяет, **кто и к чему имеет доступ** при каждом запросе. Распространенная причина этого — **IDOR**(Небезопасная прямая ссылка на объект): если изменение идентификатора (например `?id=7 → ?id=6`, ) позволяет вам просматривать или редактировать данные другого пользователя, то контроль доступа нарушен.

==🔵**IDOR** (Insecure Direct Object Reference — небезопасная прямая ссылка на объект)==

На практике это проявляется как горизонтальное повышение привилегий (та же роль, но доступ к данным другого пользователя) или вертикальное повышение привилегий (переход к действиям, доступным только администратору), поскольку приложение слишком доверяет клиенту.

Не каждое приложение предоставляет ссылки на объекты в виде текстовых значений. Разработчики часто **кодируют** идентификаторы перед включением их в строки запросов, данные POST или cookie. Кодирование преобразует необработанные данные в строку, безопасную для ASCII, используя символы `a-z`, `A-Z`, `0-9`, и `=`для заполнения. Цель состоит в том, чтобы гарантировать, что принимающий сервер сможет обработать значение без неправильной интерпретации специальных символов.

Строки base64, как правило, заметно длиннее, чем представляемое ими значение, и часто заканчиваются одним или двумя `=`символами заполнения.

В некоторых приложениях идентификаторы **хешируются** перед включением в запросы. Хешированное значение отображается в виде строки шестнадцатеричных символов фиксированной длины, что может создать впечатление, будто ссылка скрыта. Однако, если входные данные для хеш-функции предсказуемы (например, последовательное целое число), злоумышленник может воспроизвести процесс хеширования и сгенерировать действительные ссылки на любой объект в системе.

В некоторых приложениях используются случайно сгенерированные строки, UUID или другие форматы идентификаторов, которые невозможно угадать или перечислить.

Стандартный подход к тестированию в этой ситуации — это **метод двух учетных записей** :

1. Создайте две учетные записи в приложении (Учетная запись A и Учетная запись B).
2. Войдите в учетную запись A и запишите идентификаторы, связанные с ее ресурсами (профиль).(например, ссылки на порядок, пути к документам и так далее).
3. Войдите в учетную запись B и замените идентификаторы учетной записи A в запросах учетной записи B.

Если сервер возвращает данные учетной записи A учетной записи B, значит, конечная точка не выполняет надлежащие проверки авторизации. Формат идентификатора не имеет значения для этого теста. Важно то, проверяет ли сервер право собственности перед возвратом объекта.

На практике непредсказуемые идентификаторы проникают по различным каналам. Они могут появляться в общих URL-адресах, API ответы, содержащие ссылки на ресурсы других пользователей, исходный код HTML, файлы JavaScript, электронные письма с уведомлениями или экспортированные данные, такие как отчеты CSV. После получения действительного идентификатора из любого из этих источников, использование IDOR ничем не отличается от случая с открытым текстом.

==🔴Контроль доступа== — это механизм безопасности, используемый для управления тем, каким пользователям или системам разрешен доступ к определенному ресурсу или системе. Контроль доступа внедряется в компьютерные системы для обеспечения того, чтобы доступ к ресурсам, таким как файлы, каталоги, базы данных и веб-страницы, имели только авторизованные пользователи. Основная цель контроля доступа — защита конфиденциальных данных и обеспечение доступа к ним только для тех, кто имеет на это право.

Контроль доступа может быть реализован различными способами в зависимости от типа защищаемого ресурса и требований безопасности системы. К числу распространенных механизмов контроля доступа относятся:

1. **Дискреционное управление доступом (DAC)** : В этом типе управления доступом владелец ресурса или администратор определяет, кому разрешен доступ к ресурсу и какие действия им разрешено выполнять. DAC широко используется в операционных системах и файловых системах. Проще говоря, представьте себе замок, где король может раздавать ключи своим советникам, позволяя им открывать любые двери по своему усмотрению, когда им вздумается. Вот что такое DAC. Это свобода контролировать доступ к собственным ресурсам. Тот, кто отвечает за доступ, как король замка, может раздавать разрешения кому угодно, диктуя, кто может входить и выходить.
2. **Обязательный контроль доступа (MAC)** : В этом типе контроля доступа доступ к ресурсам определяется набором заранее определенных правил или политик, которые обеспечиваются системой. MAC обычно используется в средах с высоким уровнем безопасности, таких как правительственные и военные системы. Проще говоря, представьте себе крепость с железным протоколом безопасности. Только определенные лица с определенным уровнем допуска могут получить доступ к определенным зонам, и это не подлежит обсуждению. Высшее командование устанавливает правила, и они строго соблюдаются. Вот как работает MAC. Это как строгий офицер службы безопасности, который не допускает исключений из правил.
3. **Управление доступом на основе ролей (RBAC)** В этом типе управления доступом пользователям назначаются роли, определяющие их уровень доступа к ресурсам. RBAC широко используется в корпоративных системах, где пользователи имеют разные уровни полномочий в зависимости от своих должностных обязанностей. Проще говоря, представьте себе современную корпорацию. У вас есть менеджеры, руководители, сотрудники отдела продаж и т. д. У каждого из них разный доступ к зданию. Некоторые могут войти в зал заседаний, другие — в торговый зал и так далее. В этом и заключается суть RBAC — назначение доступа на основе роли человека в организации.
4. **Управление доступом на основе атрибутов (ABAC)** : В этом типе управления доступом доступ к ресурсам определяется набором атрибутов, таких как роль пользователя, время суток, местоположение и устройство. ABAC широко используется в облачных средах и веб-приложениях. Проще говоря, представьте себе высокотехнологичную научно-фантастическую систему безопасности, которая сканирует людей по определенным атрибутам. Возможно, она проверяет, с какой планеты они родом, используют ли они определенное устройство или пытаются ли получить доступ к ресурсу в определенное время. Это и есть ABAC. Это как интеллектуальная, гибкая система безопасности будущего.

Уязвимости, связанные с неработающим контролем доступа, относятся к ситуациям, когда механизмы контроля доступа не обеспечивают надлежащего ограничения доступа пользователей к ресурсам или данным. Вот несколько распространенных способов эксплуатации уязвимостей, связанных с неработающим контролем доступа, и примеры:

1. **Горизонтальное повышение привилегий**  происходит, когда злоумышленник может получить доступ к ресурсам или данным, принадлежащим другим пользователям с тем же уровнем доступа. Например, пользователь может получить доступ к учетной записи другого пользователя, изменив идентификатор пользователя в URL-адресе.
    
2. **Вертикальное повышение привилегий** происходит, когда злоумышленник может получить доступ к ресурсам или данным, принадлежащим пользователям с более высоким уровнем доступа. Например, обычный пользователь может получить доступ к административным функциям, манипулируя скрытым полем формы или параметром URL-адреса.
	
3. **Недостаточные проверки контроля доступа** возникают, когда проверки контроля доступа выполняются неправильно или непоследовательно, что позволяет злоумышленнику их обойти. Например, приложение может позволять пользователям просматривать конфиденциальные данные без проверки их соответствующих прав доступа.
    
4. **Небезопасные прямые ссылки на объекты** возникают, когда злоумышленник может получить доступ к ресурсу или данным, используя уязвимость в механизмах контроля доступа приложения. Например, приложение может использовать предсказуемые или легко угадываемые идентификаторы для конфиденциальных данных, что облегчает доступ к ним для злоумышленника.

Существует несколько шагов, которые можно предпринять для снижения риска возникновения уязвимостей контроля доступа в системе PHP приложений:
1. ***Внедрить управление доступом на основе ролей ( RBAC )*** — это метод регулирования доступа к компьютерным или сетевым ресурсам на основе ролей отдельных пользователей в рамках предприятия. Определяя роли в организации и назначая им права доступа, можно контролировать, какие действия пользователь может выполнять в системе. Приведенный фрагмент кода иллюстрирует, как можно определить роли (например, «администратор», «редактор» или «пользователь») и связанные с ними разрешения. Функция `hasPermission` проверяет, имеет ли пользователь определенной роли указанное разрешение.

```
// Define roles and permissions
 $roles = [
     'admin' => ['create', 'read', 'update', 'delete'],
     'editor' => ['create', 'read', 'update'],
     'user' => ['read'],
 ];

 // Check user permissions
 function hasPermission($userRole, $requiredPermission) {
     global $roles;
     return in_array($requiredPermission, $roles[$userRole]);
 }

 // Example usage
 if (hasPermission('admin', 'delete')) {
     // Allow delete operation
 } else {
     // Deny delete operation
 }
```

2. ***Используйте параметризованные запросы :*** Параметризованные запросы — это способ защиты PHP-приложений от SQL-инъекций, в результате которых злоумышленники могут получить несанкционированный доступ к вашей базе данных. Используя заполнители вместо прямого включения пользовательского ввода в SQL-запрос, вы можете значительно снизить риск SQL-инъекций. Приведенный пример демонстрирует, как можно сделать запрос безопасным с помощью подготовленных операторов, которые отделяют синтаксис SQL от данных и безопасно обрабатывают пользовательский ввод.

```
 // Example of vulnerable query
 $username = $_POST['username'];
 $password = $_POST['password'];
 $query = "SELECT * FROM users WHERE username='$username' AND password='$password'";

 // Example of secure query using prepared statements
 $username = $_POST['username'];
 $password = $_POST['password'];
 $stmt = $pdo->prepare("SELECT * FROM users WHERE username=? AND password=?");
 $stmt->execute([$username, $password]);
 $user = $stmt->fetch();
  
```

3. ***Правильное управление сессиями :*** Правильное управление сессиями гарантирует, что авторизованные пользователи получают своевременный и надлежащий доступ к ресурсам, тем самым снижая риск несанкционированного доступа к конфиденциальной информации. Управление сессиями включает использование защищенных файлов cookie, установку тайм-аутов сессий и ограничение количества активных сессий у пользователя. Приведенный фрагмент кода показывает, как инициализировать сессию, установить переменные сессии и проверить действительность сессии, проверив время последней активности.

```
 // Start session
 session_start();

 // Set session variables
 $_SESSION['user_id'] = $user_id;
 $_SESSION['last_activity'] = time();

 // Check if session is still valid
 if (isset($_SESSION['last_activity']) && (time() - $_SESSION['last_activity'] > 1800)) {
     // Session has expired
     session_unset();
     session_destroy();
 }
  
```

4. ***Используйте безопасные методы кодирования :*** Безопасные методы кодирования включают в себя способы предотвращения появления уязвимостей в системе безопасности. Разработчики должны проверять и подтверждать пользовательский ввод, чтобы предотвратить нанесение вреда вредоносными данными, и избегать использования небезопасных функций или библиотек. Приведенный пример показывает, как проверить пользовательский ввод с помощью filter_inputфункции PHP и демонстрирует, как безопасно хешировать пароль, используя password_hashвместо небезопасной функции, такой как md5.

```
 // Validate user input
 $username = filter_input(INPUT_POST, 'username', FILTER_SANITIZE_STRING);
 $password = filter_input(INPUT_POST, 'password', FILTER_SANITIZE_STRING);

 // Avoid insecure functions
 // Example of vulnerable code using md5
 $password = md5($password);
 // Example of secure code using password_hash
 $password = password_hash($password, PASSWORD_DEFAULT);
  
```
